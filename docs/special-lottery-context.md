# 특별추첨 기능 작업 컨텍스트

## 1. 문서 목적

이 문서는 S-ANGEL 프로젝트에 여러 날짜의 명단을 한 번에 추첨하고 조정할 수 있는
`특별추첨` 기능을 추가하기 위한 결정 사항과 작업 범위를 기록한다.

새로운 대화나 작업 환경에서도 이 문서만 읽고 다음 작업을 이어갈 수 있도록,
현재 문제와 확정된 정책, 미확정 정책, 구현 순서와 배포 주의사항을 함께 정리한다.

## 2. 현재 프로젝트

- Django 5.1 기반 서버 렌더링 애플리케이션
- 기본 브랜치: `main`
- 원격 저장소: `https://github.com/JungGyul/s-angel.git`
- 주요 코드:
  - 활동/추첨/회계/캘린더 모델: `s_angel/applications/models.py`
  - 활동/추첨/회계/캘린더 뷰: `s_angel/applications/views.py`
  - URL: `s_angel/applications/urls.py`
  - 활동 대시보드: `s_angel/templates/applications/dashboard.html`
  - 당첨자 조정 화면: `s_angel/templates/applications/review_winners.html`
- 배포: GitHub 저장소의 브랜치를 Render 서비스가 추적하는 구조

현재 일반 추첨은 활동 하나씩 다음 순서로 처리한다.

1. 활동 신청
2. 임시 추첨
3. 관리자 명단 조정
4. 활동 확정
5. 당첨자는 사용자 가중치를 1로 초기화
6. 탈락자는 사용자 가중치를 1 증가

## 3. 해결하려는 문제

여러 날짜의 활동을 연속으로 추첨할 때 앞 날짜를 최종 확정하기 전까지 사용자 가중치가
변하지 않는다. 따라서 높은 가중치를 가진 사람이 뒤 날짜의 임시 추첨에서도 계속 높은
확률로 선발된다.

각 날짜를 차례대로 확정하면 다음 문제도 생긴다.

- 날짜 확정 순서에 따라 최종 가중치가 달라질 수 있다.
- 전체 날짜의 명단을 함께 보고 사람을 이동하거나 교체하기 어렵다.
- 명단을 조정한 뒤 어느 결과를 기준으로 가중치를 정산해야 하는지 불명확하다.
- 확정 요청이 동시에 또는 중복 실행되면 가중치가 여러 번 변경될 수 있다.

## 4. 확정된 제품 방향

### 4.1 특별추첨 묶음

여러 날짜의 기존 활동을 하나의 특별추첨 묶음으로 연결한다.

- 일반 활동과 일반 추첨 흐름은 그대로 유지한다.
- 특별추첨에 속한 활동들은 전체 날짜를 한 번에 임시 추첨한다.
- 동일 사용자가 여러 날짜에 반복 선발되는 것을 허용한다.
- 이미 다른 날짜에 선발됐다는 이유만으로 다음 날짜 추첨에서 제외하지 않는다.

### 4.2 통합 명단 조정

특별추첨 결과는 하나의 통합 화면에서 조정한다.

- 날짜별 임시 당첨 명단 표시
- 사용자 추가 및 제외
- 필요한 경우 날짜 사이 이동
- 사용자별 신청 횟수 표시
- 사용자별 최종 선발 횟수와 선발률 표시
- 전체 묶음의 가중치 정산 결과 미리보기

### 4.3 묶음 단위 최종 확정

- 각 날짜를 따로 확정하지 않는다.
- 관리자가 모든 날짜의 명단 조정을 마친 뒤 특별추첨 묶음을 한 번만 확정한다.
- 가중치도 개별 날짜가 아니라 최종 확정된 전체 묶음 결과를 기준으로 한 번만 정산한다.
- 확정 이후에는 같은 묶음이 다시 확정되지 않도록 서버에서 막는다.

### 4.4 신청 대비 가중치 정산

첫 구현은 `신청 대비 방식`으로 시작한다.

개인 선발률:

```text
개인의 최종 선발 횟수 / 개인의 특별추첨 내 신청 횟수
```

특별추첨 전체 선발률:

```text
특별추첨의 전체 최종 선발 건수 / 특별추첨의 전체 신청 건수
```

초기 정산 규칙:

- 개인 선발률이 전체 선발률보다 낮으면 사용자 가중치 `+1`
- 개인 선발률이 전체 선발률과 같으면 사용자 가중치 유지
- 개인 선발률이 전체 선발률보다 높으면 사용자 가중치를 `1`로 초기화
- 한 특별추첨 묶음에서 가중치 증가량은 최대 `+1`
- 신청하지 않은 사용자의 가중치는 변경하지 않음
- 실제 변경 전에 관리자에게 기존 값과 변경 예정 값을 보여줌

정산은 반드시 관리자가 조정한 최종 명단을 기준으로 한다. 임시 추첨 결과는 가중치에
영향을 주지 않는다.

> 이 규칙은 첫 구현 정책이다. 실제 운영 후 필요하면 전체 선발률 계산을 날짜별 경쟁률,
> 성별 모집 인원 또는 지원 가능 조건까지 반영하는 방식으로 확장할 수 있다.

## 5. 추첨 방식 구현 결정

### 5.1 임시 추첨 방식

특별추첨을 만들 때 운영자가 다음 방식 중 하나를 선택한다.

1. 가중치 반영 + 반복 선발 완화
2. 기존 가중치 그대로 반영
3. 모든 신청자 동일 확률

기본값은 1번이다. 기존 사용자 가중치를 사용하되, 같은 특별추첨에서 이미 뽑힌 횟수가
늘어날 때마다 임시 추첨에 사용하는 유효 가중치를 `기존 가중치 / (선발 횟수 + 1)`로
낮춘다. 반복 선발은 모든 방식에서 허용한다.

### 5.2 확정 후 수정

첫 구현에서는 확정 이후 수정과 재정산을 막는 것을 기본값으로 한다. 확정 취소 기능이
필요하다면 가중치 변경 이력을 별도로 저장하고 정확히 되돌리는 기능을 먼저 설계해야 한다.

### 5.3 지원 방식

현재처럼 날짜별 활동에 각각 신청하게 할지, 특별추첨 묶음 화면에서 가능한 날짜를 한 번에
선택하게 할지는 별도 UI 작업으로 확장할 수 있다. 첫 구현에서는 기존 활동별 신청 정보를
재사용하는 방향을 우선 검토한다.

## 6. 제안 데이터 구조

구현 시 현재 모델과 마이그레이션 이력을 확인한 뒤 이름은 조정할 수 있다.

### 6.1 `SpecialLotteryGroup`

예상 필드:

- 설명
- 임시 추첨 완료 여부
- 최종 확정 여부
- 생성 일시
- 확정 일시
- 확정한 관리자
- 추첨 방식

### 6.2 기존 `Event` 확장

- 특별추첨 묶음을 가리키는 nullable 외래키
- 일반 활동은 외래키가 비어 있음
- 묶음 안의 날짜별 정렬 순서가 필요하면 별도 순서 필드 추가

### 6.3 가중치 정산 이력

중복 정산 방지와 결과 추적을 위해 사용자별 정산 이력 모델 추가를 우선 검토한다.

예상 저장 내용:

- 특별추첨 묶음
- 사용자
- 신청 횟수
- 최종 선발 횟수
- 개인 선발률 계산에 필요한 값
- 변경 전 가중치
- 변경 후 가중치
- 정산 일시

특별추첨 묶음과 사용자 조합에는 DB 유일성 제약을 두어 동일 사용자가 두 번 정산되지
않도록 한다.

## 7. 데이터 무결성과 동시 실행

특별추첨 최종 확정은 다음 작업을 하나의 원자적 작업으로 처리한다.

1. 특별추첨 묶음 DB 행 잠금
2. 아직 확정되지 않았는지 재확인
3. 최종 날짜별 명단 저장
4. 사용자별 신청 및 선발 횟수 집계
5. 가중치 정산 이력 저장
6. 사용자 가중치 변경
7. 특별추첨 묶음 확정 처리

프로젝트에는 요청 단위 트랜잭션 설정이 있지만, 동시에 들어온 두 확정 요청을 막기 위해
`transaction.atomic()`과 `select_for_update()`를 명시적으로 사용한다.

그 밖의 안전장치:

- 같은 사용자의 동일 활동 중복 신청을 DB 제약으로 방지
- 확정 요청은 POST로 제한
- 추첨 및 확정 버튼을 처리 중 비활성화
- 확정된 특별추첨은 다시 임시 추첨하거나 명단을 변경할 수 없음

신청, 취소, 일반 추첨, 일반 활동 삭제는 기존 구현이 아직 GET 요청을 사용한다. 이들은
6단계 대시보드 사용성 작업에서 POST로 전환해야 한다.

## 8. 화면 새로고침 문제

현재 활동 신청과 취소는 일반 링크 요청 후 대시보드로 리다이렉트되므로 전체 페이지가
새로 로딩되고 스크롤이 맨 위로 이동한다.

개선 방향:

- 신청과 취소를 POST 요청으로 변경
- JavaScript `fetch`를 사용해 비동기로 요청
- 성공 시 해당 활동 카드의 버튼과 상태만 변경
- 현재 스크롤 위치 유지
- 처리 중 버튼 비활성화
- 성공과 오류는 화면을 가리지 않는 알림으로 표시
- JavaScript가 동작하지 않을 때는 기존 POST 후 리다이렉트 방식으로 처리

특별추첨 구현과 별개의 작은 단계로 나눠 적용하고 테스트할 수 있다.

## 9. 마이그레이션과 Render 배포

모델을 변경할 때 반드시 Django 마이그레이션 파일을 생성하고 Git에 포함한다.

개발 작업:

```bash
python manage.py makemigrations
python manage.py migrate
```

배포 작업:

- 생성된 `s_angel/applications/migrations/*.py` 파일을 커밋
- Render 배포 시 `python manage.py migrate` 실행
- 마이그레이션 성공 후 새 애플리케이션 버전 실행

현재 저장소에는 `build.sh`가 있으며 `render.yaml`의 Build Command가 이를 실행한다.
스크립트는 의존성 설치, 운영 설정 마이그레이션, 정적 파일 수집을 순서대로 실행하고
하나라도 실패하면 빌드를 중단한다. 운영 배포 전에는 Render DB 백업과 실제 Dashboard의
Build Command/Auto-Deploy 설정을 별도로 확인한다.

Render가 GitHub의 `JungGyul/s-angel` 저장소 `main` 브랜치에 연결되어 있고 Auto-Deploy가
활성화되어 있다면 `git push origin main` 이후 자동 배포된다. Git clone으로 로컬 폴더를
복원한 사실은 배포 방식에 영향을 주지 않는다.

## 10. 구현 순서

### 1단계: 기반 모델

- 특별추첨 묶음 모델
- 기존 활동과 묶음 연결
- 가중치 정산 이력 모델
- 모델 제약과 마이그레이션
- Django Admin 등록

### 2단계: 특별추첨 생성 및 관리

- 관리자가 특별추첨 묶음 생성
- 기존 또는 신규 활동을 묶음에 연결
- 묶음 상세 화면

### 3단계: 전체 임시 추첨

- 묶음에 속한 모든 활동을 한 번에 추첨
- 반복 선발 허용
- 추첨 방식 정책 적용
- 임시 결과 저장

### 4단계: 통합 명단 조정

- 날짜별 명단 편집
- 사용자별 신청 횟수, 선발 횟수, 선발률 표시
- 모집 인원과 실제 선발 인원 검증

### 5단계: 최종 확정과 정산

- 정산 결과 미리보기
- 묶음 단위 최종 확정
- 원자적 가중치 변경
- 중복 확정 방지 및 정산 이력 저장

### 6단계: 대시보드 사용성

- 신청 및 취소 POST 전환
- 비동기 처리
- 스크롤 위치 유지와 인라인 상태 갱신

### 7단계: 배포

- 전체 테스트
- 마이그레이션 파일 확인
- Render 마이그레이션 명령 보강
- GitHub `main` push
- Render 배포 로그와 실제 DB 마이그레이션 확인

## 11. 필수 테스트

- 일반 추첨 동작이 기존과 동일하게 유지되는지
- 여러 활동이 하나의 특별추첨 묶음에 연결되는지
- 동일 사용자가 여러 날짜에 반복 선발될 수 있는지
- 명단 조정 결과가 신청 및 선발 횟수에 정확히 반영되는지
- 개인 선발률과 전체 선발률 계산이 정확한지
- 가중치 증가가 묶음당 최대 1인지
- 전체 선발률보다 많이 선발된 사용자의 가중치가 1로 초기화되는지
- 확정을 두 번 요청해도 가중치가 한 번만 변경되는지
- 확정 중 오류가 발생하면 명단, 이력, 가중치가 모두 원래 상태로 돌아가는지
- 신청 및 취소 후 페이지가 맨 위로 이동하지 않는지
- JavaScript 없이도 신청 및 취소가 가능한지
- 기존 PostgreSQL 데이터에 마이그레이션을 적용해도 데이터가 보존되는지
