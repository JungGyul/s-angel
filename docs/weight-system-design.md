# 가중치 시스템 재설계안 (검토용)

작성: 2026-11-15 · 상태: **확정 (사용자 결정 반영) — §7이 최종 사양**

## 1. 지금 방식

- `User.weight` 숫자 하나를 직접 바꾼다.
- 일반 의전 **확정 시**: 당첨자 → 1로 초기화, 미당첨자 → +1.
- 특별추첨 **묶음 확정 시**: 신청 대비 선발률로 +1 / 유지 / 1로 초기화.
- 추첨 시: 가중치 3 이상은 우선 선발, 나머지는 가중치 비례 추첨.
- 임시 추첨(확정 전)은 가중치에 아무 영향이 없다.

## 2. 지금 방식에서 생기는 문제

| # | 상황 | 문제 |
|---|---|---|
| A | 의전 1을 추첨하고 확정 전에 의전 2를 추첨 | 의전 2는 의전 1의 결과를 모른 채 옛 가중치를 쓴다 → **가중치 높은 사람이 연달아 둘 다 뽑힘** (특별추첨이 생긴 이유) |
| B | 의전 1·2를 **확정하는 순서**가 바뀜 | 같은 결과인데 최종 가중치가 달라짐. 예) 1 당첨·2 탈락: 1→2 순서면 `1 → 2`, 2→1 순서면 `+1 → 1` |
| C | 확정된 의전 삭제, 관리자가 가중치 직접 수정 | 기록이 없어서 **되돌리거나 다시 계산할 수 없음** |
| D | 앞 의전 명단을 나중에 조정 | 이미 그 결과를 전제로 뽑은 뒤 의전 명단과 어긋남 (요청하신 방식에서 생기는 문제) |

## 3. 제안: “가중치 = 확정된 결과를 날짜순으로 다시 계산한 값”

가중치를 숫자 하나로 덮어쓰지 않고, **결과 기록(원장)** 을 남긴 뒤 그 기록을 **의전 날짜 순서대로 재생**해서 계산한다.

```
기준값(배포 시점 가중치)
 → 11/05 의전: 당첨 → 1
 → 11/16 의전: 탈락 → 2
 → 관리자 수정: 3으로 설정
 → 11/20 의전: 탈락 → 4      = 현재 가중치 4
```

### 3.1 두 종류의 가중치
- **확정 가중치**: 확정된 결과만 날짜순으로 재생한 값. 부원 화면·관리 화면에 보이는 값.
- **추첨용 가중치(임시 반영)**: 확정 결과 + **추첨됐지만 아직 확정 안 된 앞 날짜 의전의 임시 결과**까지 반영한 값. 새 의전을 추첨할 때만 사용.
  → 문제 A 해결: 의전 1 임시 당첨자는 의전 2 추첨 때 이미 1로 취급되어 연속 당첨이 줄어듦.

### 3.2 확정하면 최종 명단 기준으로 다시 계산
- 명단 조정 후 확정하면 **조정된 최종 명단**으로 기록을 저장하고, 영향받는 부원의 가중치를 재계산.
- 계산이 날짜순이라 **확정 순서와 무관하게 같은 결과** → 문제 B 해결.
- 삭제·수정도 기록 단위로 처리 → 언제든 재계산 가능 → 문제 C 해결.

### 3.3 앞 의전 명단이 바뀌었을 때 (문제 D)
의전 2를 이미 추첨한 뒤 의전 1 명단을 조정하면, 의전 2의 임시 명단은 “옛 가정”으로 뽑힌 것이 됨.
- 의전 2 검토 화면에 **경고**: “앞선 의전(의전 1)의 명단이 바뀌어 이 추첨에 사용한 가중치와 현재 가중치가 다릅니다.”
- 운영진이 **[다시 추첨]** 또는 **[그대로 진행]** 중 선택 (확정 전까지만).
- 자동 재추첨은 하지 않음 (운영진이 이미 손본 명단이 날아갈 수 있어서).
- 확정 후에는 최종 가중치가 날짜순 재계산으로 항상 정확하게 맞춰짐.

### 3.4 특별추첨
- 묶음 안 날짜들은 지금처럼 한 번에 추첨(반복 선발 완화 유지).
- 묶음 확정 시 정산 결과(+1/유지/초기화)를 **묶음 첫 날짜 기준의 기록 1건**으로 저장 → 같은 재생 규칙에 편입.

### 3.5 관리자 수동 수정
- “이 시점부터 N으로 설정” 기록으로 저장 (사유 선택 입력). 이후 의전 결과는 그 위에 이어서 계산.

## 4. 데이터

- 새 모델 `WeightEntry`: 부원, 출처(의전/특별추첨/수동/기준값), 기준 날짜, 종류(초기화·+1·유지·N으로 설정), 값, 생성자·시각, 메모.
- `User.weight`는 그대로 두되 **재계산된 결과를 저장하는 캐시**로 사용 (기존 화면·코드 호환).
- 배포 시 마이그레이션이 **현재 모든 부원의 가중치를 ‘기준값’ 기록으로 저장** → 지금 값 그대로 이어감.
- 일반 의전은 이미 `Application.selected` + `is_finalized`에 결과가 있으므로 기록과 교차 검증 가능.

## 5. 결정이 필요한 항목

1. 계산 순서 기준: **의전 날짜순(권장)** / 확정한 순서
2. 앞 의전 명단 변경 시: **경고 + 다시 추첨 선택(권장)** / 자동 재추첨 / 무시
3. 확정된 의전을 삭제하면: **가중치 효과도 되돌림(권장)** / 지금처럼 유지
4. “가중치 3 이상 우선 선발” 규칙: **유지(권장)** / 없애고 순수 비례 추첨

## 6. 작업 범위·위험

- 마이그레이션 1개(새 모델 + 기준값 생성), 추첨·확정·특별추첨 정산·수동 수정·삭제 로직 변경, 검토 화면 경고 UI, 테스트.
- 위험: 재계산 로직 오류 시 전 부원 가중치가 틀어질 수 있음 → 배포 전 “현재 가중치 == 재계산 가중치” 검증 테스트, 관리자용 가중치 이력 화면 제공.

## 7. 최종 결정 및 구현 사양 (사용자 결정 반영)

| 항목 | 결정 |
|---|---|
| 계산 순서 | **확정한 순서** (지금과 동일하게 확정 시점에 반영) |
| 앞 의전 명단 변경 | **무시** — 이미 뽑은 뒤 의전 임시 명단은 그대로, 확정 시 가중치만 정상 반영 |
| 확정된 의전 삭제 | **가중치 유지** (지금과 동일) |
| 3 이상 우선 선발 | **유지** |

따라서 원장 재생(날짜순 재계산) 대신 **“추첨용 임시 반영 가중치”** 만 추가한다.

1. **확정 가중치** = `User.weight` (지금처럼 확정 시점에 갱신: 당첨 → 1, 미당첨 → +1, 특별추첨은 선발률 정산).
2. **추첨용 가중치** = 확정 가중치에서 시작해, *추첨됐지만 아직 확정되지 않은* 다른 의전/특별추첨 묶음의 **현재 임시 명단**을 그 추첨 시각 순서대로 가상 적용한 값 (일반: 임시 당첨 → 1, 임시 탈락 → +1 / 특별추첨: 정산 규칙을 임시 명단에 적용). DB에는 저장하지 않고 추첨할 때 계산.
3. 새 의전(또는 특별추첨 묶음)을 추첨할 때 우선 선발·비례 추첨 모두 **추첨용 가중치**를 사용 → 확정 전 연속 추첨에서도 같은 사람이 연달아 뽑히는 문제 완화.
4. 확정 시에는 **조정된 최종 명단**으로 확정 가중치를 갱신 (임시 반영분은 계산값이라 이중 적용 없음).
5. 추첨 순서를 알기 위해 `Event.drawn_at`, `SpecialLotteryGroup.drawn_at` (nullable) 추가 — 없으면 id 순.
6. 검토 화면에 신청자별 “추첨 가중치(임시 반영)”와 “확정 가중치”를 함께 표시해 운영진이 근거를 볼 수 있게 함.
7. 감사용 `WeightChange` 기록(부원, 출처, 변경 전/후, 시각, 처리자)을 확정·수동 수정 때 남김 — Django admin에서 조회.
